# GitHub comments and checks

Phase 6.5 adds `createGitHubReporter(appId, privateKey, requestFetch?)` and a local serialized publication journal. This is an explicitly callable GitHub App adapter. No HTTP route, normal worker consumer, environment credential lookup or automatic publication is wired to it. Tests use an in-memory synthetic fetch transport and ephemeral keys; no live GitHub comment or check was created.

The publisher takes a trusted journal root, scoped publication request, and `isCurrent` callback. Scope binds tenant/run/installation/repository/PR/head SHA. The caller must resolve tenant/installation ownership and publication authority from trusted application state. `publicationApproved: true` attests that the exact Markdown has been reviewed for the destination audience, including semantic claims and redaction. A private Phase 6.4 report is not automatically approved for a PR comment. The publisher does not read private artifact storage or make public artifact links.

Each call checks installation identity/app ownership/suspension, mints a token limited to one repository with metadata read, pull requests write and checks write, and resolves canonical repository owner/name. It checks current local authority and an open same-repository PR at the immutable head before delivery and around mutations. Fork PRs are refused under the current policy. Tokens and keys are not persisted in the journal. Existing read-only ingress authorization remains unchanged.

Requests specify monotonic revisions and queued/in_progress/completed phase. Completion requires a conclusion: success, failure, neutral or cancelled. Success additionally requires explicit `coverageComplete: true`; failure requires `blocking: true`. These are trusted supervisor attestations, not calculations of coverage or semantic finding truth. Non-blocking uncertain reports can use neutral. Phase regression and conflicting content at the same revision are rejected.

The adapter maintains one comment and one check per scoped run/SHA. A deterministic opaque marker identifies its comment; check `external_id` uses the same key. Reconciliation requires the same App identity and exact head SHA. It scans at most five pages of 100 comments and check runs; a full final page cannot prove absence, so it refuses creation. Ambiguous matches or changed/missing tracked identities fail closed. It does not edit comments created by other Apps or users merely because their body contains a marker.

The local journal stores scope, remote IDs, desired revision/digest/phase, delivery state and pending-create kind. It contains no report body or credentials. Desired state is synced before mutations and pending creates are saved before POST. If a create response is lost, the next call can adopt the matching owned remote object. If no unique match is visible, it stops with delivery uncertainty instead of blindly creating another. Lost PATCH responses can retry updates to the tracked ID. Identical delivered requests with matching remote content return unchanged. Lower revisions cannot overwrite an intended newer revision, including partial delivery.

Journal directories/files are private (0700/0600), reads refuse symlinks and large files, and updates use synced temporary files plus atomic rename. A per-run lock serializes local/shared-filesystem writers; it is not a distributed database lease. Abandoned locks, lost journals and ambiguous remote state require operator reconciliation. Preserve the same durable root across retries. There is no claim of unconditional exactly-once delivery, and GitHub mutations are not atomic with local journal writes or PR head changes.

Octokit automatic retries/throttling are disabled. Individual HTTP requests time out after two seconds; authority callbacks have a two-second bound. Remote pagination is bounded. Failures reject without a published success result; the journal retains intent for recovery. Local filesystem stalls, inaccessible storage, delayed remote visibility and process crashes still need production supervision. A head change after a remote write can leave a partial/stale check or comment; Phase 6.6 handles explicit stale-result reconciliation.

The API choices were checked against GitHub's primary references: [issue comments](https://docs.github.com/en/rest/issues/comments) and [check runs](https://docs.github.com/en/rest/checks/runs). Live installation permissions and hosted behavior remain unverified. No permission widening or fallback token is attempted after an API denial.
