# Model adapter and browser loop

Phase 5.3 adds a provider-neutral JSON transport adapter and a callable bounded observation–proposal–execution loop. `npm run browser-loop:verify` uses real Chromium with a deterministic offline transport. It verifies wiring and policy behavior, not live-model intelligence. No provider SDK, endpoint, model selection, credential lookup or external request is configured.

`createJsonBrowserModel(transport)` accepts a trusted transport callback. Requests contain a fixed instruction, a supervisor-provided synthetic goal, a finite action menu, an explicitly untrusted accessibility snapshot and PNG, and token ceilings. Replies must be at most 8 KiB of JSON matching `{ action, usage: { inputTokens, outputTokens } }`. There are no tool calls, scripts, raw fill values or free-form explanations. Invalid replies stop the loop without retry.

`runBrowserLoop(config, executor, model, options)` takes ownership of an already created executor and closes it on every exit, including invalid configuration. It validates immutable scope and an explicit `syntheticModelInput: true` attestation, performs the trusted initial navigation, then observes → checks scope/current authority → reserves capacity → asks the adapter → validates the proposal → executes → observes again. Bootstrap navigation is outside the model-call count but consumes executor action/request budgets. Executor replies and observations must match tenant, run, repository, PR and SHA.

Only exact configured action-menu entries or stop are accepted. The executor independently rechecks target and network permission. Page text/images remain untrusted; instructions in them cannot enlarge the action menu. This does not prove resistance to every prompt injection: an injected page could influence the choice among allowed actions. Configure the smallest useful menu and use synthetic fixture data only. The model receives no scope identifiers, origin, credentials, synthetic value map or prior raw diagnostics. Captures can still contain synthetic field values; the attestation is a trusted caller obligation, not automatic redaction. No customer captures should be supplied.

The loop caps model calls, total reserved tokens, repetitions of each exact action across the run, wall time and cleanup wait. It reserves the full input/output ceiling before each call and never refunds unknown or unused capacity. Reported usage over a ceiling is rejected before acting. Reservations are conservative local accounting, not a dollar-spend ledger or proof of actual vendor billing. Transports must enforce request/token limits, bound network response buffering, honor abort and report accurate usage. A timeout race cannot kill a callback that ignores cancellation. Production needs provider-specific verification and durable whole-run budgets.

An explicit model stop yields `status: stopped`, never passed. Budget exhaustion, incompatible observations, invalid replies, unavailable actions and cleanup failure remain inconclusive. Results contain scope, fixed codes, usage/reservations and a bounded action-kind trace; they omit page content, images, goals, action parameters and raw errors. Cleanup has a fresh independent deadline. A cleanup timeout is reported as unverified completion, not proof that resources disappeared.

Observation and executor session limits still apply and may stop before the loop limit. The loop does not detect application defects or infer success from a click; independent observations and later evidence/replay stages must establish those claims. Personas, budget-ledger integration, controlled chaos, replay and production model/browser orchestration remain later work. Normal worker startup remains dispatch-only.
