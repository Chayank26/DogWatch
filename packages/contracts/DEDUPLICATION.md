# Finding deduplication

Phase 6.2 exports `deduplicateFindings(records, trustedScope, now)` and `FindingGroup` from `@dogwatch/contracts`. This is a callable Node.js utility over v2 records, not a worker consumer or publisher. Every record is validated for current scope and evidence expiry before grouping. Invalid batches throw without returning partial results.

The conservative identity includes tenant/run/repository/PR/SHA, environment, tier, target, category, severity, confidence, title, expected/actual behavior, ordered reproduction steps, redaction attestation, confirmation-basis kind, and baseline status/base scope. It excludes finding IDs, creation time, evidence IDs and metrics. Those excluded fields remain in the retained original records. Reference arrays are sorted by artifact ID, while reproduction-step order remains significant. Text is not fuzzily matched or semantically interpreted beyond the v2 schema's existing trim behavior.

Each group has a version-domain-separated SHA-256 ID, a deterministic representative finding ID (lexicographically first), sorted full member records, and sorted unique evidence IDs. The hash is an identity fingerprint, not encryption, proof of a common root cause, or a durable globally unique finding ID. Group IDs are scoped to this run/SHA and algorithm version. A representative is only a display selection; it does not replace the other members or gain their confidence.

Exact repeated input with the same finding ID collapses into one record and increments `duplicateInputCount`. The same ID with different normalized content is a conflict, even if only a timestamp or reference changed. Distinct IDs with equivalent observation identity remain separate members of one group. Across the batch, one artifact ID must always have identical reference metadata; changed hashes, expiry or scope are rejected. Refresh conflicting reference metadata upstream rather than silently choosing one version here.

All member evidence, reproduction steps, metrics and timestamps remain inspectable. Metrics are not summed because repeated observations may overlap. Group category counts count groups, not attempts, failures across time or successful journeys. An empty batch reports zero groups; it is not proof of a passing run. Coverage gaps, advisories and uncertain regressions never merge into confirmed failures. Severity, confidence and baseline claims are never promoted by duplicate count.

Groups that reference the same artifact are linked with `kind: shared_evidence`. This can connect API and browser observations while preserving distinct tiers and targets. It states only reference overlap, not causation. There is no model-based correlation, inferred shared bug, automatic cross-tier merge or human correlation override in this phase.

Input is bounded to 100 records and 2 MiB of normalized UTF-8 record data, counting exact retries toward the byte limit. Limits reject the batch explicitly rather than silently truncating evidence. Validation returns detached records; grouping never mutates callers' objects. Outputs remain private reviewed-redacted finding data, not a general redaction guarantee. Source parsing/validation still belongs inside a resource-controlled caller for hostile input.

Artifact existence, ownership, digest integrity and supporting content must be verified through authorized storage. Deduplication does not load artifacts, verify the producer's assertions, persist groups or publish a report. Phase 6.3 addresses private artifact integration; current schemas and smoke storage remain separate until that work is implemented.
